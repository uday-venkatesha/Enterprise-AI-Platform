# Enterprise AI Platform — Project Overview

This document explains, in plain English, what this project is, how it's put
together, and what each folder does. It's meant to be a map you can come back
to at any point to re-orient yourself.

## What this thing actually does

It's a **multi-tenant document platform**: companies ("organizations") sign
up, their users log in, and they upload documents (PDF, Word, PowerPoint,
Excel, plain text). In the background, the platform:

1. Stores the raw file safely.
2. Pulls the text out of it.
3. Splits that text into small overlapping chunks.
4. Turns each chunk into a vector embedding (a list of numbers that captures
   its meaning, generated by OpenAI).
5. Saves the chunks + vectors in the database.

The end goal of steps 3–5 is to support **semantic search / RAG** (retrieval-
augmented generation) later — i.e. "ask a question, find the most relevant
chunks of your company's documents, feed them to an AI." That search/AI layer
hasn't been built yet — what exists so far is everything needed to get
documents in, processed, and embedded, ready to be searched.

Every table (users, documents, chunks) is tagged with an `organization_id`,
and every query is filtered by it. This is what makes it "multi-tenant" —
Company A can never see Company B's data, enforced in the database queries
themselves, not just in the UI.

## The big picture: how a document flows through the system

```
User uploads a file
   │
   ▼
FastAPI web server (src/app/api/documents.py)
   │  1. checks file type & size
   │  2. stores raw bytes in MinIO (object storage)
   │  3. saves a row in Postgres (filename, owner, status="uploaded")
   │  4. hands off a background job to Celery/Redis  ──► returns instantly to the user
   ▼
Celery worker (src/app/worker/tasks.py) picks up the job later
   │  1. downloads the raw bytes from MinIO
   │  2. extracts plain text (PDF/DOCX/PPTX/XLSX-specific logic)
   │  3. splits the text into overlapping ~800-character chunks
   │  4. calls OpenAI to turn each chunk into a vector embedding
   │  5. saves all chunks + vectors into Postgres
   │  6. marks the document "processed" (or "failed")
```

The key idea: uploading is instant for the user because the slow parts
(reading the file, calling OpenAI) happen in a separate background process,
not while they're waiting on the HTTP request.

## Folder-by-folder breakdown

### `src/app/` — the actual application code

Everything the app does lives under here. It's organized by *responsibility*,
not by feature — e.g. all database models live together, all API routes live
together, etc.

#### `src/app/api/` — the HTTP endpoints (the "front door")

Each file is a group of related URLs (a FastAPI "router"):

- **`auth.py`** — `/auth/login`. Takes an email + password, checks them, and
  hands back a signed JWT token (like a temporary ID badge) if they're
  correct. Deliberately gives the same error for "wrong password" and
  "no such user" so attackers can't tell which emails are registered.
- **`users.py`** — create users (admin-only), see your own profile
  (`/users/me`), list all users in your organization.
- **`organizations.py`** — create a new organization (a new "tenant"/company).
- **`documents.py`** — upload a file, list your org's documents, fetch one
  document's details. This is where the upload validation and MinIO/Celery
  hand-off happens (see flow diagram above).
- **`health.py`** — `/health` (is the process alive?) and `/ready` (can it
  actually reach the database?). Used by things like load balancers/Docker to
  know if the app is working.
- **`deps.py`** — not a router, but the security backbone every other route
  leans on:
  - `get_current_user`: reads the JWT from the request, verifies it, and
    loads the logged-in user.
  - `require_role(...)`: a reusable "only admins" / "only managers" gate —
    returns 403 Forbidden if your role isn't allowed.
  - `get_current_organization_id`: pulls the org id *from the authenticated
    user's own token*, never from something the client could fake in the
    request. This one function is what prevents Company A from ever passing
    in Company B's org id and seeing their data.

#### `src/app/models/` — the database tables (SQLAlchemy ORM)

Each file is one table, described as a Python class:

- **`organization.py`** — a tenant/company. Just an id, name, created date.
- **`users.py`** — a login account. Belongs to one organization, has a
  hashed password (never the real password), and a `role`
  (`admin` / `hr` / `manager` / `employee`) used for permission checks.
- **`document.py`** — one uploaded file's metadata: filename, size, MIME
  type, which org/user it belongs to, the MinIO storage key, and a `status`
  that tracks its lifecycle: `uploaded → processing → processed` (or
  `failed`). Also holds the full extracted text once processing finishes.
- **`chunk.py`** — one small slice of a document's text, plus its OpenAI
  embedding vector (a 1536-number list, matching OpenAI's
  `text-embedding-3-small` model). Each chunk also carries `organization_id`
  directly (not just via the document) so that future search queries can
  filter by tenant without doing an extra join.

#### `src/app/schemas/` — the "public shape" of data (Pydantic models)

These define what a request/response is allowed to look like on the wire —
separate from the database model. The most important pattern here: a `User`
database row has a `hashed_password` field, but `UserRead` (the schema
returned by the API) simply doesn't include it — so there's no way for a
password hash to accidentally leak in an API response, even in a bulk list.

- `user.py`, `organization.py`, `document.py`, `token.py` — one pair
  (`...Create` / `...Read`) per resource, matching the models above.

#### `src/app/services/` — the actual business logic

Routes in `api/` stay thin (parse the request, call a service, return the
result); the real logic — and every database query — lives here:

- **`user.py`** — look up users by id/email, create a user (hashing their
  password first), list users scoped to one org.
- **`organization.py`** — create an organization.
- **`document.py`** — create a document row, list a org's documents (newest
  first), fetch one document *only if it belongs to the requesting org*
  (returns nothing otherwise — the route turns that into a 404, so a user
  can't even tell whether a document belonging to another company exists),
  and save a batch of processed chunks+embeddings.

#### `src/app/core/` — shared low-level building blocks

Utility code that doesn't belong to any one feature:

- **`security.py`** — password hashing (bcrypt) and JWT token
  creation/verification. This is where "does this password match" and "issue
  a login token" actually happen.
- **`storage.py`** — talks to MinIO (S3-compatible object storage) using the
  `boto3` AWS SDK. Because MinIO speaks the same protocol as real AWS S3,
  this exact code would work against production S3 by just changing a
  config value — no code changes needed. Handles: making sure the bucket
  exists, uploading a file's bytes, downloading them back.
- **`embeddings.py`** — calls OpenAI's embeddings API to turn a batch of text
  chunks into vectors in a single API call (cheaper/faster than one call per
  chunk).

#### `src/app/extraction/` — turning files into plain text

One file per format, each doing the format-specific work of pulling out
readable text:

- **`pdf.py`** — uses `pypdf` to read each page's text and join them.
- **`docx.py`** — uses `python-docx` to read every paragraph in a Word doc.
- **`pptx.py`** — uses `python-pptx` to walk every slide → every shape → every
  text frame → every paragraph, since text in a slide deck is nested inside
  shapes rather than being flat text.
- **`xlsx.py`** — uses `openpyxl` to read every sheet, every row, joining a
  row's cell values with `" | "` so the spreadsheet's column structure stays
  visible to a human/AI reading the extracted text.
- **`dispatcher.py`** — the traffic cop: given a file's MIME type, picks
  which of the four extractors above to call.
- **`chunking.py`** — `chunk_text()`: splits a long string into ~800-character
  pieces with a 150-character overlap between consecutive pieces (so a
  sentence that gets cut in half at a chunk boundary still appears whole in
  the *next* chunk too — nothing meaningful gets lost at the seams).

#### `src/app/worker/` — the background job processor (Celery)

This is a **separate running process** from the web server — it's what
performs the slow work asynchronously:

- **`celery_app.py`** — sets up the Celery application, pointing it at Redis
  as both the job queue ("broker") and the place results get stored.
- **`tasks.py`** — the actual job: `process_document`. Given a document id, it
  downloads the file, extracts text, chunks it, embeds the chunks via OpenAI,
  saves everything, and updates the document's status at each stage
  (`processing` → `processed`, or `failed` if anything throws).
- **`db.py`** — a *synchronous* database connection, separate from the web
  server's async one. Celery tasks are plain synchronous functions, so the
  worker can't reuse the API's async database engine — it needs its own.

#### `src/app/db/` — database plumbing shared by the whole app

- **`session.py`** — creates the async database connection pool used by the
  web server, and `get_db()`, the FastAPI dependency every route uses to get
  a database session for the duration of one request.
- **`base.py`** — the common base class every model inherits from. SQLAlchemy
  uses it to keep track of every table that exists, which is what Alembic
  (the migration tool) reads to figure out what's changed.

#### `src/app/config.py` — all the app's settings in one place

A single `Settings` object, loaded from environment variables / a `.env`
file: database URL, JWT secret, MinIO credentials, Celery/Redis URLs, OpenAI
key, upload size limit, etc. Nothing else in the codebase hardcodes these —
they all read from here, which is what lets the exact same code run
differently locally vs. in Docker vs. in production, just by changing
environment variables.

#### `src/app/main.py` — where the FastAPI app is assembled

Creates the `FastAPI` app object, wires in logging, makes sure the MinIO
bucket exists on startup, and registers all the routers from `api/` so their
URLs actually become reachable.

### `alembic/` — database migrations

Alembic is the tool that turns "I changed a SQLAlchemy model" into "run this
SQL to update the actual database." Each file in `alembic/versions/` is one
incremental change, in order:

1. `8d98a8311d1b_...` — create `organizations` and `users` tables
2. `a96cdaa0cbc2_...` — create `documents` table
3. `642e544ac6bf_...` / `cb998362293a_...` — add `status` and
   `extracted_text` columns to `documents`
4. `88a15833b079_...` — create `chunks` table
5. `ec3343b1ea2d_...` — add the `embedding` vector column to `chunks`

`alembic/env.py` is the config that tells Alembic how to connect to the
database and which models to compare against. `alembic.ini` is Alembic's
top-level settings file.

### `tests/`

- **`test_health.py`** — hits `/health` using FastAPI's in-process
  `TestClient` (no real server needs to be running) and checks it responds
  correctly.
- **`test_security.py`** — checks password hashing actually hashes (never
  stores the plain password) and that verifying a correct vs. wrong password
  behaves correctly.

### Root-level files

- **`docker-compose.yml`** — defines and wires together every service this
  project needs to run locally:
  - `api` — the FastAPI web server
  - `worker` — the Celery background worker (same codebase, different
    command)
  - `db` — Postgres (using the `pgvector` image, since it needs to store
    embedding vectors, not just normal columns)
  - `redis` — the job queue Celery uses
  - `minio` — S3-compatible object storage for the raw uploaded files
  - Inside this network, services talk to each other by name (`db`,
    `redis`, `minio`) rather than `localhost`, since each runs in its own
    container.
- **`Dockerfile`** — how to build the image that both `api` and `worker` run
  from (they share the same code, just start with different commands).
- **`pyproject.toml` / `requirements.txt` / `uv.lock`** — Python dependencies.
- **`.env` / `.env.example`** — local environment variables (secrets,
  connection strings) — `.env` is the real one (gitignored), `.env.example`
  is a template showing what's needed.
- **`pytest.ini`** — pytest configuration.
- **`main.py`** (repo root) — a leftover placeholder script from the
  project's initial scaffolding; the real application entry point is
  `src/app/main.py`.

## Security model, in plain terms

- **Passwords**: never stored in readable form — only a `bcrypt` hash, which
  is one-way (you can check a password against it, but can't reverse it back
  to the original).
- **Login**: exchanges correct credentials for a **JWT** — a signed,
  time-limited token (30 minutes by default) the client then attaches to
  every future request instead of resending the password.
- **Authorization**: two layers —
  1. *Are you logged in at all?* (`get_current_user` — 401 if not)
  2. *Are you allowed to do this specific thing?* (`require_role` — 403 if
     your role isn't on the allowlist)
- **Tenant isolation**: every document/user query is filtered by
  `organization_id`, and that id always comes from the caller's own verified
  token — never from a value the client sends in the URL/body. A user
  literally cannot ask for another company's data by guessing an ID; they get
  a 404 that reveals nothing about whether the resource even exists.
- **Uploads**: restricted to an allowlist of file types and a max size before
  anything is stored; the file is saved under a random UUID name rather than
  the user-supplied filename, which avoids path-traversal tricks and name
  collisions.

## What's built vs. what's next

**Built so far:**
- Multi-tenant orgs/users with JWT auth and role-based access control
- Document upload with validation, stored in MinIO
- Async background processing via Celery + Redis
- Text extraction for PDF, DOCX, PPTX, XLSX, and plain text
- Chunking + OpenAI embeddings, stored in Postgres via `pgvector`

**Not built yet (the natural next step):**
- An actual search/RAG endpoint that takes a question, embeds it, finds the
  closest chunks in `pgvector`, and feeds them to an AI to answer — the data
  pipeline built so far exists specifically to make this possible.
